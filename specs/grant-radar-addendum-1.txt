GRANT RADAR ADDENDUM — FAVORITES, APPLICATION TRACKING, VERIFICATION, AND COMMUNITY MONEY COUNTER

Add these features to the Grant Radar page built from the main Grant Radar spec. These are additions only — nothing in the existing Grant Radar spec changes.

——

FEATURE 1: SAVED GRANTS (FAVORITES)

Every grant result card gets a save button in the top right corner. The icon is a small bookmark shape — a simple inline SVG, 16px, color #7a7570 when unsaved, color #8a6830 (signal gold) when saved. Tapping it saves or unsaves the grant. No confirmation required. The state changes instantly.

HOW SAVED GRANTS PERSIST

Saved grants are stored in a saved_grants table in Supabase with: user_id, grant_name, grant_url, grant_description, grant_amount, jurisdiction (Federal / State / Local), date_saved, and the full grant result JSON.

Saved grants do NOT disappear when the monthly rescan runs. The rescan replaces unsaved results but keeps saved grants in place permanently until the member manually unsaves them.

If the monthly rescan finds that a saved grant may have changed status, add a small chip to the saved card: "Status may have changed — verify before applying" in the amber chip style. Never remove saved grants automatically — always let the member decide.

THE SAVED SECTION

At the top of the Grant Radar page, above the Federal / State / Local results sections, add a SAVED GRANTS section. Collapsed by default with a toggle: "SAVED GRANTS ([N])" where N is the count. Tapping expands it to show all saved grant cards with a small note in Space Mono 9px color #7a7570 showing the date saved.

FEATURE 2: APPLICATION TRACKING WITH VERIFICATION

Every grant result card — both in the main results and in saved grants — has two action buttons at the bottom below the "View application →" button.

BUTTON 1: "I applied for this"

Ghost button style. Space Mono, 10px, uppercase, color #3a3530, border 1px solid #c8c0b0.

When clicked the button changes to a filled confirmed state: background #ece7dc, color #0a0a0f, text "Applied ✓" and a small inline form appears below with one field:

"When did you apply?"
Date input, pre-filled with today's date.
Small save button: "Save" in ghost style.

Stores in grant_applications table in Supabase: user_id, grant_name, grant_url, grant_amount_available, date_applied, outcome (null), amount_received (null), verified (false), verification_image_url (null).

BUTTON 2: "I received this grant"

This button is greyed out and disabled until Button 1 has been clicked and saved. Once the member has marked a grant as applied, Button 2 activates.

Label: "I received this grant"
Ghost button style, same as Button 1.

When clicked show an inline flow with three steps:

STEP 1 — Amount received:
"Congratulations. How much were you awarded?"
Number input with dollar sign prefix, required.

STEP 2 — Upload verification document:
"Upload proof of award to verify your win."
File upload field accepting: JPG, PNG, PDF only. Maximum file size 10MB.

Below the upload field, a plain English explanation in Space Grotesk 11px color #5a5650:
"This can be your official award letter, a grant agreement, a check image, a bank deposit confirmation, or any government document showing the grant amount and your business name. Your document is stored privately and is only reviewed by The Bridge team. It is never shared publicly. Your name is never displayed on the counter — only the dollar total changes."

STEP 3 — Submit button:
"Submit for verification →" in primary button style.
Disabled until both the amount and a document have been provided.

On submission: store the amount and the uploaded document URL in the grant_applications table. Set verified to false and status to "pending_review." Do not update the community money counter yet.

THE VERIFICATION PROCESS — MANUAL REVIEW BY YOU (THE BRIDGE OWNER)

This is intentionally a human verification step, not automated. You review submissions and approve them before the counter updates. Here is how it works:

ADMIN NOTIFICATION
When a member submits a grant win for verification, send an email notification to the Bridge admin email address (set this in the environment variables as ADMIN_EMAIL). The email contains:
- Member's business name
- Grant name
- Amount claimed
- A secure link to view the uploaded document
- Two buttons: "Approve this win" and "Reject this submission"

The secure link and buttons use a signed URL with a one-time token so only you can access them. They do not require logging into a separate admin panel.

APPROVE FLOW
Clicking "Approve this win" in the email calls an internal API route: POST /api/admin/grant-verify?token=[signed_token]&action=approve
This sets verified to true in grant_applications, sets status to "verified", writes to the grant_wins table (user_id, grant_name, amount_received, date_verified, jurisdiction), and triggers the community money counter to update.

The member receives an email: "Your grant win has been verified. Your contribution has been added to The Bridge community total. Thank you for sharing your win — it helps other captains know what is possible."
Space Grotesk voice, warm, brief.

REJECT FLOW
Clicking "Reject this submission" calls the same route with action=reject.
This sets status to "rejected" and sends the member an email: "We were not able to verify your grant win from the document provided. This could be a formatting issue or an incomplete document. You are welcome to resubmit with a different document — award letters, grant agreements, or bank confirmation statements work best."
No accusatory language. Treats every rejection as a document problem, not a fraud accusation.

MEMBER-FACING STATUS
After submission Button 2 changes to show one of three states:
- "Verification pending" — amber chip, Space Mono 9px
- "Win verified ✓" — green chip, Space Mono 9px
- "Resubmit document" — with a small reupload link

FEATURE 3: THE COMMUNITY MONEY COUNTER

A live counter on the landing page showing the total verified grant money secured by Bridge members. Only verified wins from the grant_wins table contribute to this number. Unverified submissions never touch the counter.

THE COUNTER ON THE LANDING PAGE

Add a new section to the landing page between the Problem section and the Solution section. Dark background #08080f, same as the hero, so it separates the two cream sections visually.

Content centered, max-width 700px:

LABEL:
"GRANT MONEY SECURED BY THE BRIDGE COMMUNITY"
Space Mono, 10px, color #c8a96e, letter-spacing 0.15em, uppercase, margin-bottom 1rem.

THE NUMBER:
Total from the grant_wins table where verified = true, summed from amount_received.
Font: Space Mono, clamp(2.5rem, 8vw, 5rem), color #f0ebe0, font-weight 700, letter-spacing 0.05em.
Formatted as a dollar amount with commas: "$47,500" or "$1,240,000."
Shows $0 if no verified wins exist yet. The section still displays at $0 — this is honest and will not stay at zero long.

BELOW THE NUMBER:
"In free government grant money that Bridge members found, applied for, and won."
Space Grotesk, 1rem, color #b8b0a0, text-align center, margin-bottom 0.5rem.

"Verified. Real. Theirs to keep."
Space Grotesk, 1rem, color #5a8a6a, font-style italic, text-align center.

ANIMATION: When the section enters the viewport via IntersectionObserver, the number counts up from 0 to the actual total over 2 seconds with ease-out timing. Runs once per page visit. If the total is $0 the animation does not run — just shows $0 immediately.

THE PUBLIC API ENDPOINT

The landing page fetches the current total from: GET /api/grant-radar/community-total

This endpoint queries the grant_wins table where verified = true, sums amount_received, and returns: { "total": 47500 }

This is a public endpoint — no authentication required. It returns only an aggregate number, zero personal data. Cache the response for 1 hour to avoid unnecessary database queries on every page load.

THE DOCUMENT UPLOAD — STORAGE

Use Supabase Storage for the verification documents. Create a private bucket called grant-verification-documents. Files are never publicly accessible — only accessible via signed URLs generated server-side. The admin verification email links use signed URLs with a 72-hour expiry so you have time to review them.

File naming convention: [user_id]/[grant_application_id]/[original_filename]
